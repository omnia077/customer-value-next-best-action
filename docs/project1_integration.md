# Connecting Project 1's churn scores

Project 2 needs a churn probability for each subscriber. Committed results use a simple stand-in (`src/churn_proxy.py`) so that anyone can reproduce them from a clone. Project 1 (Telecom-Churn-Platform, `ml_churn/`) has the real model. This page records how it was connected, what it changes, and what it does not.

## Why Project 1 had to be re-run on this dataset
Project 1's checked-in data and Project 2's data have the **same 20,000 customers** (IDs, MSISDNs, regions, plans, activation dates are identical) but **different behaviour**: Project 1 was built on the plain simulator (212,164 recharges), Project 2 on the simulator with planted archetypes and campaigns (205,823 recharges). Scores from one world do not describe the other, so Project 1 was re-run on Project 2's dataset (`data_v2/`).

## What was done
1. Copied Project 1 to a **separate folder** (`Telecom-Churn-Platform_shared_data`, next to the original). All commands ran inside the copy, and the salt file was not copied. Project 1 was being edited and committed in parallel by its owner, so timestamps in the original do not show what this work touched; the copy's code matches the original's current code (see below).
2. Replaced its `src/data/sftp_drop` and `src/data/ground_truth` with Project 2's `data_v2` versions.
3. Ran, with the real salt loaded from the environment: `run_phase2.py`, `ml_churn.build_panel`, `leakage_checks` (passed), `train`, `evaluate`, and `score_monthly --as-of 2024-09-30`.
4. Ran `python src/compare_churn_sources.py --scores <churn_scores.parquet> --key sub_hash --prob probability` (needs `CHURN_HASH_SALT` in the environment). Results: `outputs/project1_comparison.json`, `project1_calibration.csv`, `project1_actions.csv` (aggregates only; no subscriber IDs).

To reproduce on your machine, repeat steps 1 to 4 (cutoff must be 30 Sep: the adapter rejects any other cutoff). To make the whole pipeline use Project 1's scores instead of the stand-in, set `churn.external_scores_path`, `key_column: sub_hash` and `prob_column: probability` in a gitignored `config/customer_value.local.yaml` and run `python src/score_monthly.py churn_scores actions persona_kpis drift_check mlflow_log`. Committed results deliberately stay on the stand-in, because the real scores need your salt and cannot be regenerated by CI.

The adapter (`src/ids.py`) reproduces Project 1's scheme, `sha256(salt + msisdn)[:16]` (a test compares it with Project 1's own `hash_id`), and fails loudly on: wrong salt (unmapped hashes), a different cutoff date, probabilities outside [0, 1], duplicate keys, or under 90% coverage. The raw MSISDN is read only to build the hash map and is never written.

## Results on the shared data (12,332 prepaid subscribers scored by both; 237 churned in October)
| | Project 1 | Stand-in |
|---|---|---|
| Project 1's own test metrics on this data (Sep-Nov) | ROC-AUC 0.808, top-decile lift 4.86, base rate 1.96% (in line with its reported numbers: the planted archetypes do not disturb it) | |
| ROC-AUC on actual October churn | **0.773** | 0.746 |
| AUC gap, Project 1 minus stand-in (paired bootstrap, 95% CI) | **+0.028 (0.010 to 0.052)** | |
| PR-AUC / top-decile lift | 0.068 / 3.80 | 0.047 / 2.91 |
| Rank agreement between the two | Spearman 0.80 | |
| Mean predicted churn vs observed 1.92% | 2.27% (1.18x) | 1.96% (1.02x) |
| Top-risk decile: predicted vs observed | 12.7% vs 7.3% (1.7x) | 8.4% vs 5.7% (1.5x) |

**Decision layer under each source** (same budget, same assumptions):

| | Stand-in | Project 1 |
|---|---|---|
| Retention (protect) actions | 221 | 337 |
| Recharge bonus / win-back | 2,963 / 692 | 2,865 / 674 |
| Expected net value | 365k SDG | 390k SDG |
| Retention expected value | 25k SDG | 55k SDG |
| Actual October churn rate in the group selected for retention | 3.9% | **7.1%** (population 1.9%) |

## What to conclude
- Project 1's model is **measurably better at ranking risk** than the stand-in (AUC gap significant), and it picks retention targets that really do churn more (7.1% vs 3.9%).
- Its **probability level is still somewhat high, most of all in the top decile** (1.7x), so its retention expected value (55k SDG) is probably overstated. Treat it mainly as a ranking, and check calibration on recent labelled data before quoting the money.
- **Project 1's calibration change worked, and it is visible here.** An earlier run of Project 1 on this same data, made before its calibration was switched from isotonic regression on one validation month to Platt scaling on pooled out-of-fold predictions, trained the same model (126 trees, identical validation PR-AUC), ranked subscribers almost identically (Spearman 0.996 with the later run) but predicted a mean churn about 1.5x the observed rate (mean 2.81% vs 1.92% observed on the subscribers scored by both). The table above uses the current code (`train.py`, `model.py`, `evaluate.py`, `score_monthly.py` and `config.yaml` are byte-identical to the Project 1 folder as it stood when this was written), where the ratio is 1.18x. An earlier version of this page wrongly blamed run-to-run instability; the difference came from the code change.
- **Some over-prediction remains at the top.** The highest-risk decile is still predicted at 12.7% vs 7.3% observed, so retention value, which is driven by the top of the ranking, is probably still overstated.
- With 237 churners, all October comparisons are noisy; the AUC gap and the 7.1% vs 3.9% difference are the parts that are clearly beyond noise.
- Nothing in the uplift, CLV or segmentation results depends on this choice; retention is about 7% (stand-in) to 14% (Project 1) of the expected value.
